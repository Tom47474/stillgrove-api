# Stillgrove 数据库设计文档

## 1. 范围与原则

Stillgrove 使用 MySQL、Qdrant、Redis 三种存储。MySQL 是用户、会话、消息、摘要和长期记忆的权威数据源；Qdrant 只保存用于相似度检索的向量与最少量索引元数据；Redis 保存 Session、限流计数等临时数据。聊天消息不保存在 Qdrant 或 Redis 中。

长期记忆在后台自动提取、整理和同步，不在聊天过程中逐条询问用户。后台应避免把临时情绪、未经证实的推测、第三人的事实直接固化为长期记忆。用户仍应能在产品设置中管理与删除自己的数据。

## 2. 存储关系

```text
users (1) ── (1) user_credentials / user_profiles / user_settings
  ├── (N) user_consents / data_deletion_requests
  ├── (N) conversations (1) ── (N) messages
  │                   └── (0..1) conversation_summaries
  ├── (N) ai_generations
  └── (N) memories ── (N) outbox_events（通过 aggregate_id 关联）

verification_codes：按邮箱保存短期验证记录
safety_events / user_feedback：关联用户、会话或消息
consumed_events：按消费者和事件 ID 去重

memories.vector_point_id ── Qdrant Point ID
```

`outbox_events` 是通用异步事件表，因此不对 `aggregate_id` 建外键；事件中的 `aggregate_type` 表明其所属实体。

## 3. 通用约定

- MySQL 8.0+；数据库字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。
- 主键统一为 `BIGINT UNSIGNED AUTO_INCREMENT`；Java 中映射为 `Long`。单库阶段足够使用，日后如需分库再调整 ID 生成方案。
- 时间使用 `DATETIME(3)`；应用写入和读取时统一使用 UTC，前端按用户时区展示。数据库连接时区也应设置为 UTC。
- 状态、类型以 `VARCHAR` 存储；Java 枚举只允许约定值。迁移脚本不使用 MySQL `ENUM`，便于后续扩展。
- 所有面向用户的查询必须带 `user_id` 归属条件。不能只凭前端传入的 `conversation_id` 或 `memory_id` 查询。
- 消息正文、摘要与记忆正文应限制应用层长度；`TEXT` 单列上限约 64 KiB，超长消息应拒绝或分段处理。
- MyBatis Mapper 负责业务 SQL，Flyway 独立负责表结构迁移；不要让 ORM 自动建表或修改表。

## 4. MySQL 表

### 4.1 users

用户主记录，只保存账号生命周期。邮箱和密码哈希存入 `user_credentials`。`status` 可为 `ACTIVE`、`DISABLED`、`DELETION_PENDING`、`DELETED`。

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | 主键 |
| status | VARCHAR(20) | 账号状态 |
| last_login_at | DATETIME(3) | 最后登录时间 |
| deletion_requested_at / deleted_at | DATETIME(3) | 注销申请和完成时间 |
| created_at / updated_at | DATETIME(3) | 创建与更新时间 |

`user_credentials` 保存唯一邮箱、密码哈希、密码修改时间、失败次数和锁定时间；密码只能保存安全哈希。`user_profiles` 保存昵称、头像 URL、语言和时区；`user_settings` 保存通知配置和内部长期记忆处理标志。长期记忆策略由后台自动处理，不向用户提供逐条确认或保存策略选择。注册时在一个事务中创建这四张表的记录。`verification_codes` 保存短期验证码哈希、用途、过期时间和使用时间，不存明文验证码。

### 4.2 conversations

一个用户可拥有多个会话。`next_sequence` 在事务中锁定会话行后递增，用于生成消息顺序。`status` 为 `ACTIVE` 或 `DELETED`；`archived_at` 和 `deleted_at` 记录归档与删除时间。列表按 `last_message_at DESC, id DESC` 分页。

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| id / user_id | BIGINT UNSIGNED | 主键与用户归属 |
| title | VARCHAR(120) | 会话标题 |
| status | VARCHAR(20) | 会话状态 |
| next_sequence | INT UNSIGNED | 下一条消息序号，从 1 开始 |
| last_message_at | DATETIME(3) | 最近消息时间，可为空 |
| created_at / updated_at | DATETIME(3) | 创建与更新时间 |

索引：`(user_id, status, last_message_at, id)`。

### 4.3 messages

保存用户原话和 AI 完整回复。`role` 为 `USER` 或 `ASSISTANT`，`status` 为 `PENDING`、`COMPLETED` 或 `FAILED`。`content_type` 当前为 `TEXT`，`error_code` 记录失败分类，`deleted_at` 支持软删除。流式回复开始前可创建空内容的 `PENDING` 助手消息，完成后一次性更新正文；不把每个 SSE 片段插入数据库。

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| id / user_id / conversation_id | BIGINT UNSIGNED | 主键、用户与会话 |
| sequence_no | INT UNSIGNED | 会话内消息序号 |
| role / status | VARCHAR(20) | 角色与生成状态 |
| content | TEXT | 消息正文 |
| created_at / updated_at | DATETIME(3) | 创建与更新时间 |

约束：`UNIQUE(conversation_id, sequence_no)`；查询索引 `(conversation_id, sequence_no)`。消息的 `user_id` 必须在服务层与会话归属核对。

### 4.4 ai_generations

记录模型请求、幂等请求号、关联消息、供应商与模型、耗用 Token、耗时、成本微单位、结束原因、重试次数和失败状态。`client_request_id` 由前端为一次发送生成；同一次重试沿用原 ID。`status` 为 `RUNNING`、`COMPLETED` 或 `FAILED`。`cost_micros` 必须配合应用统一约定的币种与计价来源使用，不能直接把估算值当账单。

约束：`UNIQUE(user_id, client_request_id)`；`user_message_id`、`assistant_message_id` 分别唯一，避免同一消息被多个生成任务引用。可为空的 Token 字段以模型返回的实际用量为准。

### 4.5 conversation_summaries

每个会话最多一条当前摘要。`covered_sequence_no` 表示已概括到哪条消息；构建模型上下文时使用该摘要及其后的近期消息，避免重复注入同一段历史。`version` 用于并发更新，`status` 和 `model_name` 记录生成状态与模型。

约束：`UNIQUE(conversation_id)`。

### 4.6 memories

长期记忆的权威正文。`category` 可取 `PREFERENCE`、`BACKGROUND`、`GOAL` 等；`status` 为 `ACTIVE`、`EXPIRED` 或 `DELETED`。`source_conversation_id`、`source_message_id` 用于追溯来源；来源被清理时按产品数据删除策略同步处理记忆。`confidence` 为 0 到 1 的后台提取置信度，不能单独作为真实性保证。`version` 每次修改递增。

`vector_point_id` 是稳定的 Qdrant Point UUID。`last_verified_at`、`invalidation_reason`、`deleted_at` 支持后台重新判断和删除。记忆内容变化时重新计算向量并覆盖同一个 Point；删除时先将 MySQL 状态设为 `DELETED`，再异步删除 Point。检索结果回查 MySQL，只使用归属正确、`ACTIVE`、未过期、版本匹配的记忆。

索引：`(user_id, status, expires_at, id)`；`UNIQUE(vector_point_id)`。

### 4.7 outbox_events

记忆写入或删除时，同一 MySQL 事务中写入事件。后台发布器扫描 `NEW`/待重试事件并投递 RocketMQ，Worker 执行 Embedding 与 Qdrant 更新。字段包括 `aggregate_type`、`aggregate_id`、`aggregate_version`、`event_type`、`payload`、`status`、`attempts`、`next_retry_at`、`last_error`。

`event_type` 目前使用 `MEMORY_UPSERT`、`MEMORY_DELETE`。`max_attempts`、`sent_at` 记录重试上限与投递时间。Worker 通过 `consumed_events` 按消费者和事件 ID 幂等处理，并重新读取 MySQL 当前版本；旧版本事件不可覆盖新版本向量。若消息系统暂不可用，Outbox 仍可重试。`SENT` 表示事件已成功投递，不等于 Qdrant 已写入；消费者还需自己的重试和死信处理。

### 4.8 账号、删除与安全辅助表

| 表 | 用途与关键约束 |
| --- | --- |
| `verification_codes` | 邮箱验证码哈希、用途、过期和使用时间；定期清理。发送频率另用 Redis 限制。 |
| `user_consents` | 记录账号层面的协议/隐私文本类型、版本和接受时间；不参与逐条记忆保存决策。`(user_id, document_type, document_version)` 唯一。 |
| `data_deletion_requests` | 记录用户数据删除任务的范围、状态、请求和完成时间；任务失败可重试。 |
| `safety_events` | 记录风险分类、级别和处理动作，仅关联消息 ID，不额外复制对话原文。 |
| `user_feedback` | 用户对某条 AI 消息的评价；`(user_id, message_id)` 唯一。 |
| `consumed_events` | Worker 消费事件的幂等记录；`(consumer_name, event_id)` 为主键。 |

执行账号删除时，先禁止登录并使相关 MySQL 内容不可检索，再删除 Qdrant 向量和 Redis Session，最后按依赖顺序清理明细。当前外键不设级联删除，不能只删除 `users` 一行；删除任务需要明确的服务端编排和失败重试。

## 5. Qdrant 设计

Collection：`stillgrove_memories`。向量维度与距离函数取决于最终选定的 Embedding 模型，创建 Collection 时以模型实际输出维度为准，不在 SQL 中硬编码。

```text
Point ID = memories.vector_point_id (UUID)
Vector   = memories.content 的 Embedding
Payload  = { user_id, memory_id, version, category }
```

为 `user_id` 创建 payload 索引。检索时必须以 `user_id` 过滤；命中的 `memory_id` 再回查 MySQL。Qdrant 不保存正文，不承担授权判断。摘要向量如后续确需跨会话检索，再建立独立 Collection，并以 MySQL 摘要记录为权威来源。

## 6. Redis 设计

- Spring Session：登录态与过期时间。
- 限流：用户或 IP 的短周期计数。
- 可选缓存：允许失效后从 MySQL 重建的数据。

Redis 不保存唯一的一份会话、消息或记忆正文。

## 7. 核心写入与读取流程

### 发送消息

1. 校验当前用户拥有该会话，检查 `client_request_id` 是否已处理。
2. 在事务中分配两个消息序号，写用户消息、空的 `PENDING` 助手消息和 `RUNNING` 生成记录。
3. 调用模型，通过 SSE 返回片段。
4. 模型完成后，在事务中写完整助手内容和 Token 用量、更新状态及 `last_message_at`；失败时写失败状态。

模型调用不能包在长时间持有数据库锁的事务中。

### 自动形成记忆

完整对话产生后，后台提取候选内容，自动完成过滤、去重、合并和过期判断。有效记忆及 `outbox_events` 在同一事务中写 MySQL；异步 Worker 调用 Embedding 并更新 Qdrant。此流程不阻塞用户当前回复，也没有逐条确认界面。

### 检索记忆

用户消息 → 查询向量 → Qdrant 按 `user_id` 检索候选 ID → MySQL 批量回查 → 检查归属、状态、过期时间和版本 → 选取少量记忆拼入模型上下文。

## 8. 数据量与安全

百万用户不意味着立即分库分表；先观察消息总量、写入速率、慢查询、索引大小，再决定归档和分片。列表及消息历史使用游标分页，避免深度 `OFFSET`。不要在日志、Outbox payload 或 RocketMQ 消息中复制完整对话正文；通过 ID 回查。生产环境使用独立数据库账号、最小权限、传输加密、备份及恢复演练。删除用户数据时，先使 MySQL 数据不可检索，再同步删除 Qdrant 索引及按保留策略清理备份。
